# 가설 검증과 커버리지의 의미

이 문서의 기본 원칙은 **관찰, 주장, 검증을 별도 기록으로 남기는 것**이다. agentcov가 어떤 줄을 읽었다고 기록해도 그 줄의 동작을 이해했거나 결함이 없음을 뜻하지 않는다. 누군가 같은 가설을 먼저 등록했어도 그 결론이 맞다는 뜻이 아니다.

## 1. 세 종류의 기록

| 기록 | 답하는 질문 | 답하지 못하는 질문 |
| --- | --- | --- |
| agentcov 열람 기록 | 어느 에이전트가 어느 코드 줄을 도구로 읽었나? | 제대로 이해했나? 위험을 모두 찾았나? |
| 가설 | 무엇이 사실일 수 있다고 생각하나? | 참인가? |
| 검증 시도 | 누가 어떤 방법으로 반례 또는 미결 결과를 얻었나? | 한 번의 결과만으로 최종 진실인가? |
| 취약점 보고 | 어떤 가설에서 PoC와 KASAN 로그를 얻었나? | 서버가 실제 인과관계까지 입증했나? |

중앙 서버는 이 세 기록을 연결하되 하나로 환산하지 않는다. 열람률은 **도구에서 관측된 코드 노출의 지도**이고, 가설 상태는 **검증의 현재 상태**다. 기록이 없는 줄도 다른 경로로 보았을 가능성이 있으며, 기록된 줄도 실제로 이해했다고 증명할 수 없다. 열람률 100%여도 미검증 가설이 남을 수 있다. 열람률이 높은 파일도 독립 검증의 대상이 될 수 있다.

## 2. 한 가설에 여러 검증 시도

```text
가설 H-001: 입력 길이 검증이 특정 경로에서 우회된다
  ├─ A의 직접 재현: PoC + KASAN 보고
  ├─ B의 경계값 테스트: 반박
  ├─ C의 다른 입력 테스트: 미결
  └─ 사람의 판정: 아직 없음
```

가설은 에이전트가 독점하는 작업이 아니다. 서버는 **같은 가설의 두 번째 분석을 막지 않는다.** 여러 시도는 같은 `hypothesis_id`에 붙는다. 충돌 방지는 동일한 파일 편집이나 실험 장비 점유 같은 **실제 공유 자원**에만 적용한다. 같은 주장을 같은 방법으로 다시 검사하는 일도 `replication`으로 명시하면 허용한다.

반례나 미결 결과는 검증 시도로 기록한다. `verdict`의 `supports`는 이전 기록과의 호환을 위해 받아들이지만, 취약점 보고의 필수 단계나 폐기 수치에는 사용하지 않는다. 실제 PoC와 KASAN 로그가 있으면 가설에서 바로 `finding`을 보낸다. `prior_exposure`는 검증자가 기존 결과를 얼마나 봤는지(`none`, `claim_only`, `summary`, `full`) 남기는 참고 정보다.

## 3. 새 가설을 던지기 전의 가벼운 검증

1. `search_hypotheses`로 비슷한 주장과 코드 범위를 찾는다. 검색 결과는 중복 후보이지, 그 주장의 진실 판정이 아니다.
2. 현재 커밋에서 관련 코드가 실제로 존재하고, 주장한 조건·흐름이 가능한지 **최소 한 번 직접 확인**한다. 가능하면 작은 테스트·반례·정적 추적 중 하나를 남긴다.
3. 기존 가설과 같은 주장이라면 새 가설을 복제하는 대신 그 `hypothesis_id`에 **반례 또는 PoC/KASAN 보고**를 붙인다.
4. 비슷하지만 조건이나 영향이 다르면 새 가설로 등록하고 본문에 관련 가설 ID와 차이를 남긴다.
5. 빠른 검증이 불가능하면 가설을 `unverified`로 등록한다. 불확실성을 숨기거나 참·거짓으로 단정하지 않는다.

서버도 이벤트 수신 시 관련 후보를 다시 검색한다. 두 PC가 동시에 비슷한 내용을 작성할 수 있기 때문이다. 의미상 중복을 자동으로 확정하지 않고 `possible_matches`와 차이를 반환한다.

## 4. 독립 검증 모드

중요하거나 모순된 가설은 다른 에이전트에게 `claim_only` 모드로 전달한다. 이 모드는 **주장·위치·검증 계획·검증 건수·폐기 여부**를 보여주고 개별 검증의 방향·근거는 잠시 가린다. 두 번째 에이전트가 자체 추적·실험 결과를 먼저 기록한 뒤 기존 근거를 공개해 비교한다. 시간 절약이 우선인 낮은 위험 작업에서는 전체 근거를 읽고 `prior_exposure=full`로 검토해도 된다. 두 방식의 결과를 같은 독립성으로 취급하지 않는다.

## 5. 상태와 보고

자동 상태는 최종 진실 판정이 아니라 **현재 확보한 근거의 모양**이다.

- `unverified`: 검증 시도 없음
- `reported`: 실제 PoC·KASAN 보고가 있으며 반박은 없음
- `refuted`: 현재 커밋에서 한 에이전트가 반박함
- `retired`: 현재 커밋에서 서로 다른 두 에이전트가 반박함. 동일 시도를 보류하는 신호이며 PoC/KASAN 보고를 숨기지 않음
- `contested`: PoC·KASAN 보고와 한 에이전트의 반박이 함께 있음
- `inconclusive`: 시도했으나 결론을 내릴 수 없음

반박 수치는 같은 커밋의 활성 `refutes` 기록을 남긴 **고유 에이전트 ID 수**다. 같은 에이전트의 반복 기록은 한 명으로 세고, 정정된 검증은 제외한다. 같은 커밋에서 `retired`가 되면 해당 가설의 계획된 재검증을 중단한다. 반박 기록 자체가 잘못됐다면 정정한다. 코드 커밋이 바뀌면 이전 검증은 `stale`로 표시하며 새 커밋은 별도로 판단한다.

## 6. 작업 우선순위

중앙 서버는 다음 두 가지를 다음 조사 후보로 제시한다.

1. 아무도 읽지 않은 코드 영역
2. 기존 가설에 반박이 하나만 있거나 PoC/KASAN 보고와 반박이 충돌하는 영역

열람 기록은 1번을 찾는 데 유용하지만 분석 완료 여부를 뜻하지 않는다. `get_coverage_gaps`와 `get_review_gaps`는 분리해 두며, 이전 커밋의 `stale` 가설은 자동 재검증 후보로 제시하지 않는다. 이미 읽은 영역도 다시 검토할 수 있다.
