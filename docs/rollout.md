# 구현 순서와 확인 기준

중앙 서버, 로컬 동기화 에이전트, MCP와 대시보드는 구현돼 있다. 아래 단계는 각 분석 PC에서 agentcov와 토큰을 연결해 운용할 때의 확인 순서다.

## 단계 1 — 로컬 단일 에이전트

- 분석 저장소에 agentcov를 설치하고 Codex 훅 또는 세션 backfill을 연결한다.
- 로컬 MCP가 Markdown 이벤트를 `runtime/exchange/outbox/<agent-id>/`에 저장하고 즉시 전송하도록 연결한다. 로컬 동기화 프로세스는 실패한 전송을 재시도한다.
- `runtime/telemetry/progress/<agent-id>.md`와 agentcov 결과를 5분 묶음으로 만든다.
- 중앙 서버를 `127.0.0.1:8765`에 실행하고 SQLite에 이벤트·묶음을 수락한다.
- MCP에서 주장과 `code_ref`로 가설을 찾고, 발견 위치·검증 계획을 담아 등록하거나 기존 가설에 `verification` 이벤트를 붙인다.

**확인:** 가설 MD 하나가 ACK와 함께 한 번 등록된다. 같은 파일을 재전송해도 중복되지 않는다. agentcov가 읽은 한 줄은 현황판에, 읽지 않은 줄은 공백 목록에 나타난다. 이미 등록된 가설에 지지·반박 검증 이벤트를 각각 추가할 수 있다.

## 단계 2 — 같은 PC의 복수 에이전트

- 서로 다른 `agent_id`로 두 에이전트를 실행한다.
- 동일한 코드 줄을 두 에이전트가 읽어도 팀 커버리지 분자에는 한 번만 더한다.
- 각 에이전트의 고유 기여와 중복 열람을 표시한다.
- 같은 `claim_key + angle`을 두 에이전트가 동시에 검증해도 각자의 시도를 보존한다. 새 가설 수신 시 기존 후보를 반환하되 검증 자체를 차단하지 않는다.
- 한 에이전트가 지지하고 다른 에이전트가 반박하면 가설을 `contested`로 표시한다.
- 같은 커밋에서 다른 두 에이전트가 서로 다른 방법으로 독립 반박하고 지지가 없으면 `retired`로 표시한다. 새 지지 근거가 생기면 `contested`로 바뀐다.
- `claim_only` 조회는 기존 결론·근거를 숨긴다. 검증 시도에 기존 결과 노출 정도와 방법을 기록한다.
- `search_seen`과 직접 열람을 구별한다.

**확인:** 합산 열람률이 두 퍼센트의 합이나 평균이 아니며, 줄 집합의 합집합과 일치한다. 버전·커밋이 다르거나 작업 트리가 변경됐으면 별도 현황으로 표시한다. 두 에이전트 모두에게 노출된 코드라도 연결된 검증 이벤트가 없으면 `검증 기록 없음`으로 남는다.

## 단계 3 — SSH 서버와 5대 PC

- 동일한 중앙 서버 코드·SQLite DB를 SSH 서버에 옮기고 로컬 루프백에 바인딩한다.
- 각 PC의 SSH 터널과 고유 토큰·`agent_id`를 설정한다.
- 연결이 끊기면 outbox와 배치를 로컬에 보존하고, 재연결 시 같은 ID로 재전송한다.
- 서버는 각 에이전트의 마지막 수신 시각을 표시한다.

**확인:** 5대 중 한 대가 오프라인이어도 다른 네 대의 수집이 진행된다. 오프라인 PC가 복귀하면 누락된 이벤트가 중복 없이 반영된다.

## 실패·품질 기준

1. 이벤트 업로드가 실패하면 ACK를 쓰지 않는다. 원본 MD는 유지한다.
2. 묶음의 파일 해시가 맞지 않으면 전체 묶음을 거절한다.
3. 가설 검색의 유사도 결과는 참고용으로 표시한다. 기존 가설의 존재나 열람률을 조사 금지·완료 판정으로 사용하지 않는다.
4. 분모가 정의되지 않은 분석 진행도는 퍼센트 대신 작업 상태 건수를 표시한다.
5. 읽기 커버리지, 검색에서 발견된 줄, 테스트 실행 커버리지를 서로 다른 이름으로 표시한다.
6. 중앙 보고서는 어떤 에이전트·세션·커밋에서 수치가 나왔는지 추적할 수 있어야 한다.
7. 지지와 반박이 공존하면 어느 한쪽을 자동으로 숨기지 않고 `contested`로 표시한다.
